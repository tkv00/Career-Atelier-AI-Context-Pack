# 서로 다른 Notion·Excel 형식을 가져오는 설계

[README로 돌아가기](../README.ko.md) · [현재 MCP 사용법](../runner/mcp/README.md)

**상태: 확장 제안. 아래의 검사 도구·매핑 마법사·설정 저장·AI 추출은 아직 구현하지 않았습니다.** 현재 작업 폴더의 구현과 제안을 구분해 기술합니다. MCP 확장 파일은 미커밋 상태일 수 있으므로 배포된 버전과도 구분해야 합니다.

## 왜 형식을 사전에 강제하면 안 되는가

사용자는 경험을 정리할 때 서비스의 저장 구조를 알지 못합니다. “프로젝트명 / 내가 한 일 / 배운 점”이라는 엑셀, 경험마다 Notion 페이지를 만든 구조, 한 셀에 여러 사건을 적은 표는 서로 다른 문제입니다. 템플릿을 먼저 맞추라고 요구하면 가져오기 전에 다시 작성해야 하므로 기능의 가치가 줄어듭니다.

사전에 고정할 것은 **서비스 내부의 저장 계약**입니다. 원본의 열 이름과 배치는 읽은 뒤 알아내고, 그 둘을 연결하는 매핑은 사용자별로 결정합니다. LLM이 바로 DB에 쓰도록 맡기기보다 원본·변환 후보·사용자 확인·저장을 분리하는 편이 누락과 잘못된 경험 생성을 추적하기 쉽습니다.

MCP는 호스트/클라이언트가 서버의 도구를 발견하고 호출하는 규약입니다. Excel이나 Notion의 내용을 이해하는 알고리즘은 별도로 구현해야 합니다. 현재도 파서와 저장기는 MCP 밖에서 테스트할 수 있습니다. [MCP 공식 아키텍처](https://modelcontextprotocol.io/docs/learn/architecture)

## 현재 되는 것과 안 되는 것

| 항목 | 현재 작업 폴더 구현 | 한계 |
|---|---|---|
| Excel | `.xlsx`, 시트 선택, 첫 행을 헤더로 처리 | 병합 셀·수식 거부. 파일 10 MiB, 시트 10,000개 데이터 행·100열 제한 |
| 열 이름 차이 | `column_map`으로 원본 열을 `title` 또는 지원 필드로 연결 | 의미 추측·다중 열 결합·한 셀 분할은 하지 않음 |
| Notion | 페이지·DB·데이터 소스 읽기, 속성 매핑 | DB 행 본문·첨부파일은 가져오지 않음 |
| 미리보기 | `preview_import`: 종류별 건수·제목 예시·진단·digest | 필드 전체를 대조하는 검토 UI는 없음. 진단 목록도 종류별 20개로 제한 |
| 저장 | `import_records`, 기본 `dry_run=true`; digest 일치 검사 선택 가능 | `dry_run=false`면 유효한 행을 쓸 수 있음. 경고가 있다고 저장이 자동 차단되지는 않음 |
| 알 수 없는 표 열 | 경고 반환 | 값 자체는 현재 저장하지 않음 |
| 자유 서술 | 지원 구조로 정리된 Markdown·JSON | 임의 문서에서 사건·행동·성과를 자동 추출하지 않음 |

구현 근거: [표 파서](../runner/mcp/tabular.mjs), [Excel 읽기](../runner/mcp/excel.mjs), [소스 어댑터](../runner/mcp/sources.mjs), [도구·미리보기·저장](../runner/mcp/server.mjs).

## 지금 당장 가능한 매핑

사용자 A의 “경험 이름 / 성과 요약”과 사용자 B의 “활동명 / 결과”를 서비스의 `title / result`로 연결할 수 있습니다. 원본 열 이름을 바꿀 필요는 없습니다.

MCP 클라이언트에서 `preview_import`에 전달할 예시입니다. 경로와 시트명은 본인 파일의 값으로 바꿉니다.

```json
{
  "source": "/absolute/path/experiences.xlsx",
  "sheet": "경험정리",
  "section": "경험",
  "column_map": {
    "경험 이름": "title",
    "성과 요약": "result"
  }
}
```

이는 두 필드만 매핑하는 예제입니다. 나머지 실제 열도 지원 필드에 연결하고 경고를 검토해야 합니다. 저장하려면 같은 소스·시트·매핑을 `import_records`에 전달하고 `dry_run=false`를 지정합니다. 미리보기에서 받은 실제 `source_digest`를 `expected_digest`로 함께 전달하면 중간 변경을 검사합니다. 값이 없거나 거부된 행이 자동으로 보완되는 것은 아닙니다.

## 제안하는 사용자 흐름

1. **원본 선택:** Excel 파일 또는 접근 가능한 Notion 소스를 선택합니다. 원본은 수정하지 않습니다.
2. **구조 확인:** 시트·표·헤더 후보·열 자료형·행 수를 보여 줍니다. 사용자가 데이터 구간과 “한 경험의 경계”를 확인합니다.
3. **연결 제안:** “내가 한 일 → action”처럼 필드 연결을 제안합니다. 예시 값과 제안 이유를 함께 보여 줍니다. 불확실한 연결은 미정으로 남깁니다.
4. **변환 검토:** 원본 셀/블록과 저장될 값을 나란히 보여 줍니다. 저장·제외·수정할 항목을 선택하고, 누락되는 값의 처리 방법을 결정합니다.
5. **저장 계획 승인:** 생성·수정·제외·실패 예정 건수를 구분합니다. 같은 제목의 다른 경험은 자동 덮어쓰기하지 않습니다.
6. **저장 및 재사용:** 검토한 계획만 저장하고 결과를 보여 줍니다. 매핑 설정은 같은 형식의 다음 가져오기에 재사용하되 헤더와 자료형이 달라지면 재검토합니다.

초기에는 이 흐름을 MCP 도구와 대화로 제공할 수 있습니다. 최종 사용자 접근성을 위해서는 경험 카드 화면에 “자료 가져오기”를 두고 같은 변환 엔진을 호출하는 웹 마법사가 적합합니다. 파일을 로컬 Runner가 처리하도록 한다면 업로드 전달·기기 선택·Runner 미연결 상태까지 설계해야 하며, 웹이 로컬 파일을 직접 읽을 수 있다고 가정하면 안 됩니다.

## 제안 도구와 데이터 계약

아래 이름은 새 도구 제안이며 현재 호출할 수 없습니다.

| 제안 도구 | 입력 | 출력·부작용 |
|---|---|---|
| `inspect_source` | 소스와 허용된 샘플 범위 | 구조 후보, 원본 위치, 타입, 샘플. DB 쓰기 없음 |
| `propose_mapping` | 구조·대상 기록 종류 | 규칙 기반 매핑과 미정 항목. 선택적으로 AI 제안 |
| `preview_plan` | 매핑·구간·변환 규칙 | 원본/변환 값 대조, 진단, 생성·수정 계획, plan ID와 digest |
| `commit_plan` | 사용자 검토된 plan ID·digest | 계획에 고정된 대상만 저장. 변경·만료 시 재검토 요구 |

원본 위치는 Excel의 파일·시트·셀 주소, Notion의 페이지·블록·속성 ID를 보존합니다. 경로만으로 문서 내용을 재구성할 수 없으므로 원문 스냅샷을 보관할지, 해시·위치만 남길지도 사용자에게 선택하게 합니다. 스냅샷은 로컬 저장·접근 제한·만료·삭제 방법이 필요합니다.

매핑 설정에는 버전, 소스 종류, 헤더 서명, 대상 기록 종류, 필드 연결, 날짜 해석 규칙, 결합/분할 규칙을 기록합니다. 기본적으로 실제 경험 텍스트와 인증 정보는 매핑 설정에 넣지 않습니다. 다른 사용자에게 공유할 때도 문서 ID·로컬 경로를 제거합니다.

## 예외를 처리하는 기준

| 원본 사례 | 제안 처리 | 저장 조건 |
|---|---|---|
| 위에 제목·설명이 있고 4행부터 표 | 헤더 후보를 제안하고 사용자가 4행을 선택 | 선택 구간 고정 |
| 중복 열 이름 또는 두 열이 같은 필드로 연결 | 위치로 구별해 표시, 하나 선택 또는 결합 규칙 지정 | 충돌 해소 전 차단 |
| 여러 경험이 한 셀에 있음 | 분리 후보와 각 원문 범위를 표시 | 개수·경계 확인 후 저장 |
| 경험 하나가 여러 행에 걸침 | 사용자가 묶음 기준 지정, 원본 순서 보존 | 임의로 이전 행을 복사하지 않음 |
| 병합 셀·수식 | 현재는 거부. 향후 값 추출 후보를 표시하되 수식 실행은 하지 않음 | 최신 값인지 확인 불가하면 값으로 내보내기 요청 |
| “배운 점”을 성과로 볼지 불명확 | 의미를 강제하지 않고 사용자가 필드 또는 메모 선택 | 사실을 새로 만들지 않음 |
| `03/04/24`, 기간, 진행 중 | 원문 유지, 날짜 형식·연도·진행 여부 질문 | 해석 확정 또는 해당 날짜 미저장 |
| 필수 제목 없음 | 제목 후보를 제안하거나 입력 요청 | 행 제외를 명시하거나 제목 확정 |
| 알 수 없는 열 | 원문 메모 보존 또는 명시적 제외 선택 | 조용히 버리지 않음 |
| 같은 제목의 다른 경험 | 원본 ID와 내용 비교, 별개/업데이트 선택 | 제목만으로 자동 병합하지 않음 |
| Notion 접근 거부·본문 일부 누락 | 읽은 범위와 누락 범위 표시 | 불완전한 범위를 승인 없이 완전한 경험으로 취급하지 않음 |
| 미리보기 뒤 원본 변경 | 계획 만료, 다시 미리보기 | digest 일치 |
| 일부 DB 쓰기 실패 | 성공·실패 ID 구분, 재시도는 실패 대상만 | 작업 ID 기반 중복 방지 필요 |
| 원문에 “기존 자료 삭제” 같은 지시 | 원문 데이터로 취급 | 허용된 변환·저장 동작 밖의 도구 실행 금지 |

불확실한 값은 검토 대상으로 남깁니다. AI가 출력한 자신감 숫자를 검증된 확률처럼 표시하지 않습니다.

## AI는 어디에 쓰는가

표 구간·별칭·자료형이 명확한 경우 규칙으로 처리합니다. 의미가 모호한 열 이름이나 자유 서술의 사건 경계에만 사용자가 선택한 로컬 CLI를 사용하도록 확장합니다. 요청할 때 어떤 샘플이 AI 제공자에게 전달되는지 설명하고, 규칙만 사용하는 경로도 유지합니다.

AI는 매핑·변환 후보만 반환하고 DB 쓰기를 직접 결정하지 않습니다. 반환 결과를 스키마로 검증하고 원본 위치가 없는 주장·수치·성과는 검토 대상으로 돌립니다. 원문에 없던 수치를 “설득력 있게” 채우는 기능은 넣지 않습니다. CLI 제공자별 스키마는 기존 `runner/schema-compat.mjs`를 사용합니다.

## 선택지와 트레이드오프

| 방식 | 장점 | 비용·한계 |
|---|---|---|
| 고정 템플릿 | 구현·검증 간단, 재현성 높음 | 사용자가 기존 자료를 재작성 |
| 사용자 열 매핑 | 규칙 기반, 값 변형 적음 | 첫 매핑과 복잡한 구조 처리 부담 |
| 전체 문서 AI 변환 | 다양한 서술 형식 수용 가능 | 토큰·시간·비결정성·외부 전달·환각 위험 |
| 구조 검사 + 규칙 + 선택적 AI + 검토 | 표는 빠르게, 모호한 부분만 보완 | UI·계획 관리·출처 추적 구현량 증가 |

이 프로젝트에는 마지막 방식이 적합하다는 설계 판단입니다. 다양한 형식을 수용하면서 경험의 근거를 추적해야 하기 때문입니다. 모든 원본을 완벽하게 처리한다고 보장하지 않고, 지원 범위 밖에서는 원본을 보존한 채 필요한 결정을 질문합니다.

## 구현 순서와 검증

1. **읽기 전용 구조 검사:** 엑셀 헤더 위치·구간 선택, Notion 속성/본문 범위 검사부터 추가합니다. 첫 행 고정·지원 안 되는 열 손실 문제를 실제 fixture로 재현합니다.
2. **매핑 검토와 저장:** 충돌 해소, 제외 선택, 원본 대조, 설정 버전과 재사용을 구현합니다. 헤더가 바뀌면 기존 설정을 자동 적용하지 않는 회귀 테스트를 둡니다.
3. **계획 기반 저장:** digest, 만료, 원본 ID, 중복·업데이트 계획, 부분 실패와 재시도 멱등성을 검증합니다. 현재 선택적 digest만으로 완성된 승인 흐름이라고 부르지 않습니다.
4. **선택적 AI 추출:** 자유 서술·다중 사건을 지원합니다. 실제 CLI 실행과 고정 응답 테스트를 분리하고, 출처 없는 필드는 저장 후보에서 제외하는지 확인합니다.
5. **웹 가져오기 UI:** 동일 엔진을 UI에서 사용합니다. Runner 미연결, 업로드 실패, 검토 중 이탈·재개까지 사용자 과제로 검증합니다.

테스트 자료는 정답 JSON과 원본 좌표가 있는 합성 Excel/Notion 응답으로 만듭니다. 정상 표뿐 아니라 위 예외 표의 각 사례, 원본 변경, 재시도, 권한 오류를 포함합니다. 파서 단위 테스트, MCP stdio 계약 테스트, 저장 테스트 더블, 별도 개인 테스트 프로젝트의 실제 쓰기, 신규 사용자 관찰을 구분해 보고합니다. 이 제안의 테스트는 아직 실행하지 않았습니다.

## 개선 효과를 어떻게 측정할 것인가

“도입 전후”를 하나로 섞지 않습니다. **현재 열 매핑 방식 대 제안 방식**은 사용성/정확도 비교이고, **동일 변환 엔진의 직접 호출 대 MCP 호출**은 프로토콜 비용 비교입니다. MCP만 붙인 것이 정확도 개선의 원인이라고 해석하지 않습니다.

| 지표 | 측정 정의 |
|---|---|
| 완료율 | 미리 정한 완료 기준을 만족한 사용자 수 / 시도 사용자 수 |
| 작업 시간 | 원본 선택 시작부터 검토·저장 확인까지. 실패·중단도 별도 보고 |
| 필드 정확도 | 정답과 일치하는 저장 대상 필드 수 / 정답 필드 수. 누락과 오기입 별도 집계 |
