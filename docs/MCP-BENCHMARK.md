# MCP 도입 before/after — 토큰 소비량 측정

외부 정리본을 Career Atelier DB로 옮기는 작업을 **에이전트가 직접 하는 경우**와
**MCP 서버가 하는 경우**로 나눠 측정했다. 측정일 2026-09-03.

재현: `cd runner && npm run mcp:bench`

<br>

## 한 줄 요약

같은 입력(2,215자 정리본, 12개 항목)을 넣었을 때 모델이 소비하는 토큰이
**3,006 → 114로 줄었다(96.2% 감소).** MCP 툴 정의가 요청마다 붙는 고정
비용 537토큰까지 빼고 보면 **1회 임포트 기준 순절감 2,355토큰(78.3%)**이고,
임포트를 반복할수록 고정 비용이 희석돼 96%에 수렴한다.

<br>

## 무엇을 측정했는가

측정 대상은 **모델의 컨텍스트를 통과하는 텍스트**다. 서버가 디스크에서 읽거나
DB에 쓰는 양은 토큰 비용이 아니므로 제외했다.

### BEFORE — MCP 없이 에이전트가 직접

에이전트가 이 작업을 하려면 세 단계를 거쳐야 한다.

1. **원문을 컨텍스트로 읽는다.** 정리본 전체가 들어온다.
2. **구조화해 다시 뱉는다.** 읽은 내용을 표별 INSERT 인자로 재작성한다.
   원문이 사실상 **두 번** 토큰이 되는 지점이다.
3. **행마다 응답을 받는다.** 12행이면 12번.

### AFTER — MCP 툴 1회

1. **툴 호출 인자.** `{"source": "...", "dry_run": false}` — 경로 하나.
2. **영수증.** 표별 저장 건수·건너뛴 항목·경고.

원문은 서버 안에서 읽고 파싱해 DB까지 넣으므로 **모델 컨텍스트에 한 번도
들어오지 않는다.** 절감의 대부분이 여기서 나온다.

<br>

## 측정값

### 정확한 실측값 — 문자 수

토큰과 달리 문자 수는 추정이 아니라 실측이다. 1차 지표로 쓴다.

| 항목 | 문자 | 바이트 |
|---|---:|---:|
| 원문 정리본 | 2,215 | 4,623 |
| 에이전트가 재작성해야 할 INSERT 인자 | 5,687 | — |
| MCP가 돌려주는 영수증 | 295 | — |
| MCP 툴 정의 (요청마다 고정) | 1,778 | — |

INSERT 인자(5,687자)가 원문(2,215자)보다 큰 것은 JSON 구조와 필드명이
붙기 때문이다. **에이전트 방식에서 원문이 두 번 계산되는 게 아니라 2.5배로
불어난다**는 뜻이다.

## 실제 호출에서 나온 값

벤치마크 스크립트가 아니라 **서버를 실제로 돌려** 나온 계측값이다. 서버가
호출마다 `~/.career-atelier/mcp-metrics.jsonl`에 남긴다.

| 호출 | 입력 | before | after | 절감 |
|---|---|---:|---:|---:|
| `preview_import` (표본 12항목) | 2,215자 | 2,838 | 323 | 88.6% |
| `import_records` (실쓰기 3항목) | 373자 | 505 | 192 | 62.0% |

벤치마크(96.2%)보다 낮은데, 이유가 있고 숨길 이유도 없다. 실제 툴은 영수증에
**저장된 항목 제목과 표별 내역을 함께 돌려준다.** 사용자가 무엇이 들어갔는지
확인할 수 있어야 하기 때문이다. 벤치마크는 그 확인용 정보를 뺀 최소 영수증
기준이다. 즉 **96.2%는 이론 상한, 88.6%가 실사용 값**이다.

3항목짜리 실쓰기가 62%로 가장 낮은 것도 같은 이유다 — 입력이 작을수록
영수증의 고정 부분(경로·상태 필드)이 차지하는 비중이 커진다. **입력이 클수록
절감률이 올라간다**는 뜻이고, 실제 사용 시나리오(수십 개 항목이 담긴 정리본)는
표본보다 크다.

## 토큰 환산식

이 프로젝트는 API 키를 쓰지 않으므로(§19.2 #11) 공식 토크나이저를 호출할
경로가 없다. 그렇다고 출처 없는 토큰 숫자를 적는 건 더 나쁘다. 그래서
**문자 클래스별 환산식을 공개하고 그대로 적용**했다.

| 문자 클래스 | 토큰 1개당 문자 수 |
|---|---:|
| 한글 음절 (가–힣) | 1.5 |
| CJK (한자·가나) | 1.0 |
| ASCII (영문·숫자) | 3.8 |
| 그 밖의 기호 | 2.5 |
| 공백 | 6.0 |

한글을 ASCII와 같은 비율로 잡지 않은 게 중요하다. BPE 사전이 영어 중심이라
한글은 음절 하나가 토큰 1개를 넘기기도 한다. 흔히 쓰는 "4자 = 1토큰"을 한글
문서에 그대로 적용하면 **절감량을 3배쯤 부풀리게 된다.**

구현은 `runner/mcp/metrics.mjs`의 `estimateTokens()`다.

<br>

## 이 수치의 한계

포트폴리오로 쓸 자료라 과장하지 않기 위해 남긴다.

- **토큰은 추정치다.** 정확한 값은 문자 수뿐이다. 실제 토크나이저와는
  클래스별 계수만큼 오차가 있다.
- **양쪽 모두 시스템 프롬프트·대화 이력을 제외했다.** 두 경우에 동일하게
  붙는 상수라 차이에 영향을 주지 않는다.
- **에이전트 방식을 한 번에 성공한다고 가정했다.** 실제로는 파싱을 틀리거나
  스키마를 어겨 재시도가 붙는 경우가 많으므로, before는 **낙관적으로 잡힌
  값**이다. 즉 실제 절감폭은 이보다 클 가능성이 높다.
- **Notion 경로는 이 측정에 포함되지 않았다.** 자격증명이 없어 실호출을
  못 했다(자세한 사정은 [MCP-DECISION-LOG.md](MCP-DECISION-LOG.md)).
  다만 Notion이든 파일이든 파싱 이후 경로는 동일하므로, 소스를 읽는 구간만
  달라지고 절감 구조는 같다.

<br>

## 부수 효과 — 토큰 외의 이득

토큰이 목표였지만 측정 중에 드러난 것들이라 같이 적는다.

- **정확도.** 파싱이 정규식이라 결정론적이다. 같은 입력이면 항상 같은 결과가
  나오고, 모델이 필드를 잘못 옮길 여지가 없다.
- **중복 방지.** 자연키로 갱신하므로 같은 정리본을 두 번 넣어도 행이 쌓이지
  않는다(실측: 재실행 시 `created:0, updated:3`).
- **원문 비노출.** 학번·자격증 등록번호 같은 값이 모델 컨텍스트를 통과하지
  않는다. 토큰 절감을 위한 설계였는데 프라이버시 이득이 따라왔다.
