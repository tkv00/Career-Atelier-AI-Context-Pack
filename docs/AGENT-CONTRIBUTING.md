# AI 에이전트로 기여하기

이 저장소는 사람이 직접 코드를 쓰든, 코딩 에이전트에게 맡기든 같은 기준으로 검사합니다.
이 문서는 에이전트를 써서 기여할 때 무엇을 읽히고, 무엇을 실행시키고, 결과를 어떻게 확인하는지 설명합니다.

에이전트가 읽어야 할 규약 자체는 [AGENTS.md](../AGENTS.md)에 있고, 기계가 검사하는 규칙은 [docs/AGENT-RULES.md](AGENT-RULES.md)에 있습니다. 이 문서는 그 둘을 실제 작업 흐름에 어떻게 쓰는지에 대한 안내입니다.

---

## 1. 왜 규칙을 코드로 만들었나

이 프로젝트의 규약은 대부분 "지키지 않아도 빌드는 통과하는" 종류입니다.

- RLS 없는 테이블은 타입 검사도, 린트도, 빌드도 모두 통과합니다. 대신 anon 키를 가진 누구나 남의 행을 읽습니다.
- `web/`에 API 키를 하나 넣어도 앱은 잘 돕니다. 대신 이 프로젝트가 없애려던 종량제 과금이 되살아납니다.
- 이미 적용된 마이그레이션을 고치면 내 컴퓨터에서는 멀쩡합니다. 대신 남의 데이터베이스와 스키마가 갈라집니다.

에이전트는 AGENTS.md를 읽었다고 말할 수 있지만, 읽었는지 확인할 방법은 없습니다.
그래서 규약을 문장이 아니라 **실행되는 함수**로 옮겼습니다. 규칙 하나가 곧 `scripts/lib/rules.mjs`의 함수 하나이고, `docs/AGENT-RULES.md`는 그 배열에서 생성되므로 설명과 검사가 어긋날 수 없습니다.

---

## 2. 시작하기

에이전트에게 아래를 그대로 전달하면 됩니다. 저장소 루트에서 시작하는 것을 전제로 합니다.

```text
이 저장소에 기여할 거야. 먼저 AGENTS.md와 docs/AGENT-RULES.md를 읽어.
작업 전후로 `npm run rules`를 돌리고, 실패한 규칙은 검사 코드가 아니라 원인을 고쳐.
끝나면 실제로 실행해서 확인한 것과 정적 검사만 한 것을 나눠서 보고해.

할 일: (여기에 작업 내용)
```

규칙 검사는 의존성 설치가 필요 없습니다. Node 표준 라이브러리만 쓰므로 `npm install` 없이 클론 직후 바로 돌아갑니다.

```bash
npm run rules                          # 작업 트리에서 확인 가능한 모든 규칙
npm run rules -- --base origin/main    # 히스토리를 보는 규칙까지 (CI와 동일)
npm run rules -- --list                # 규칙 목록
npm run verify                         # 규칙 + 테스트 + 타입 검사 + 린트 + 빌드
```

### Claude Code 사용 시

`.claude/commands/`에 저장소가 공유하는 명령이 들어 있습니다. 클론하면 바로 쓸 수 있습니다.

| 명령 | 하는 일 |
|---|---|
| `/verify` | CI와 같은 순서로 검사하고, 실행한 것과 못 한 것을 나눠 보고 |
| `/migration` | 추가 전용·RLS·타입 재생성을 지킨 마이그레이션 추가 |
| `/new-agent` | 새 AI 비서를 러너에 끝까지 연결 |
| `/new-provider` | 새 AI CLI 프로바이더 연동 |
| `/new-rule` | 새 규약을 검사 가능한 규칙으로 추가 |

### 다른 도구 사용 시

Codex, Gemini CLI, Cursor, Copilot 코딩 에이전트는 [AGENTS.md](../AGENTS.md)를 직접 읽습니다. 별도 설정이 필요 없습니다. `CLAUDE.md`는 AGENTS.md를 가리키기만 하며, 규칙 CA011이 이 연결이 끊어지지 않았는지 검사합니다.

## 3. 규칙이 막아 주는 것

전체 목록과 실패 시 조치는 [docs/AGENT-RULES.md](AGENT-RULES.md)에 있습니다. 성격별로 나누면 이렇습니다.

| 무엇을 지키는가 | 규칙 |
|---|---|
| 데이터베이스가 갈라지지 않게 | CA001 추가 전용, CA002 번호 순서, CA009 타입 재생성 |
| anon 키로 남의 자료를 못 읽게 | CA003 모든 테이블에 RLS와 소유자 정책 |
| 종량제 과금이 되살아나지 않게 | CA004 `web/`에 자격증명 없음, CA005 `web/`은 모델을 호출하지 않음 |
| 자격증명이 공개 저장소에 남지 않게 | CA010 커밋된 키 탐지 |
| 문서와 기록이 갈라지지 않게 | CA006 README 세 판본, CA012 규칙 문서, CA013 커밋 제목 |
| 하네스가 반쯤 연결된 채 배포되지 않게 | CA011 에이전트 컨텍스트, CA014 Node 고정, CA015 프로바이더 연결 |
| 사람 판단이 필요한 것 | CA008 새 의존성 (경고로만 보고) |

히스토리를 보는 규칙(CA001, CA008, CA009, CA013)은 비교 기준이 없으면 **통과가 아니라 건너뜀**으로 보고됩니다. 얕은 클론에서 초록불이 떴는데 사실은 아무것도 검사하지 않는 상황을 막기 위해서입니다.

## 4. 규칙이 실패했을 때

검사기는 파일, 문제, 조치를 함께 출력합니다.

```text
  FAIL  CA003  Every table has RLS and an owner policy
        supabase/migrations/0034_notes.sql - table "notes" never gets "enable row level security"
        fix: Add `alter table <name> enable row level security;` and an owner policy ...
```

**검사기를 고쳐서 통과시키지 마세요.** 규칙이 틀렸다고 판단되면 `scripts/lib/rules.mjs`를 조용히 수정하는 대신 이슈나 PR 설명에 근거를 적고, 규칙은 실패한 채로 두세요. 규칙을 바꾸는 것도 정당한 기여이며, 그때는 `/new-rule`의 절차(위반 사례로 테스트를 먼저 만들 것)를 따릅니다.

CA008은 실패가 아니라 경고입니다. 새 의존성이 정말 필요한지는 사람이 판단할 문제라, 검사기는 사실만 보고하고 PR 설명에서 이유를 묻습니다.

## 5. 규칙이 검사하지 못하는 것

여기가 가장 중요한 부분입니다. **규칙 통과는 검증이 아닙니다.**

이 저장소의 버그 이력은 대부분 모든 정적 검사를 통과하고 실제로 돌려 봤을 때만 드러난 것들입니다. 없는 키를 구조 분해하던 컨텍스트 팩, 파일 경로를 받는다고 문서화되어 있지만 실제로는 JSON 문자열을 받던 CLI 플래그, JSON으로는 유효하지만 프로바이더 API가 거부하던 스키마 같은 것들입니다.

그래서 보고할 때 세 가지를 명확히 나눠 주세요.

- **실행해서 확인함** — 직접 돌려서 결과를 봤다.
- **정적 검사만 함** — 타입과 규칙은 통과했지만 그 코드가 실행되지는 않았다.
- **확인하지 못함** — 못 돌렸다. 이유도 함께. (Supabase 프로젝트가 없다, 해당 구독이 없다, tty가 없다)

"동작할 것으로 보입니다"는 세 번째 항목입니다. 솔직한 공백이 암묵적인 통과 주장보다 훨씬 쓸모 있습니다.

러너를 건드렸다면 `npm start`로 실제 작업을 하나 흘려보내고, 어느 프로바이더로 시험했는지 적어 주세요. 구독이 없어 시험하지 못한 프로바이더가 있으면 그것도 적어 주세요.

## 6. 파이프라인

`.github/workflows/ci.yml`이 모든 PR에서 세 갈래를 병렬로 돌립니다.

```text
Project rules   규칙 검사 (설치 없음, 수 초). PR이면 origin/<base>와 비교
Tests           Ubuntu / Windows / macOS x Node 22.13.0 / 24 에서 버전 검사와 테스트
Web checks      타입 검사, 린트, 프로덕션 빌드
```

규칙 잡은 실패를 GitHub 주석(`::error file=...`)으로 남기므로 PR의 해당 줄에 바로 표시되고, 작업 요약에는 무엇을 어떻게 고쳐야 하는지 표로 정리됩니다. 통과한 규칙은 요약에 넣지 않습니다. 기여자가 봐야 하는 것은 고칠 것과 검사가 실제로 돌긴 했는지 두 가지뿐입니다.

로컬에서 CI와 같은 것을 돌리려면:

```bash
npm run rules -- --base origin/main --github
```
